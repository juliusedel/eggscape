# Assumptions

Decisions made while building Eggscape without asking. Each entry says what was assumed and why, so it can be
revisited deliberately.

## Environment and tooling

- **Toolchain.** Built and tested with Xcode 27.1 (Swift 6.4, iOS 27.1 SDK) on macOS 27. The deployment target stays
  at iOS 17.0 as specified; APIs newer than iOS 17 are used only behind `#available` checks.
- **No Homebrew on the build Mac.** `brew install xcodegen` was not possible, so `scripts/bootstrap.sh` builds pinned
  versions of XcodeGen (2.46.0) and SwiftFormat (0.64.4) from source into `.tools/` (git-ignored). The Makefile
  prefers tools on `PATH`, so `brew install xcodegen swiftformat fastlane` remains the normal setup.
- **No GitHub credentials on the build Mac.** The repository could not be cloned or pushed at first, so the work
  started in a local repository whose first commit mirrored the GitHub "Initial commit". That history was later
  replayed onto GitHub's initial commit and merged into `main`.
- **fastlane is not installed on the build Mac** (system Ruby 2.6 is too old for current fastlane). The lanes are
  written and syntax-checked but could not be executed; they need `brew install fastlane` (or `bundle install`).
- **Swift 6 language mode** everywhere, with strict concurrency checking.
- **Tests** use Swift Testing for `EggscapeCore` and the app unit tests, and XCTest for the UI tests (Swift Testing has
  no UI testing support).
- **Simulator builds are unsigned** (`CODE_SIGNING_ALLOWED=NO`) in the Makefile and CI, so they work while
  `DEVELOPMENT_TEAM` is still the `<TEAM_ID>` placeholder.
- **Info.plist is maintained by hand** in `App/Info.plist` (not generated by XcodeGen), so the file is reviewable and
  the build number (`CFBundleVersion = $(CURRENT_PROJECT_VERSION)`) follows agvtool.
- **`make test`** runs the core package tests and the app unit tests as specified. The UI test (a full race) runs with
  `make test-ui` because it takes a few minutes.
- **`UIRequiresFullScreen`** is set as specified even though iPadOS 26 deprecated it; it is harmless on iPhone, and
  the app is iPhone-only (`TARGETED_DEVICE_FAMILY = 1`), so iPads run it in iPhone compatibility mode.
- **MultipeerConnectivity is deprecated in the iOS 27 SDK** ("Use Network Framework instead"). It still works and the
  spec asks for it, so Nearby play uses it, but only behind a small transport protocol so a Network framework
  implementation can replace it later without touching the lobby or race logic.

## Product direction changed by the owner (2026-10-27)

See `docs/ARCHITECTURE.md` for the full list. Consequences for the original spec:

- **§8 art direction is replaced.** Instead of a cartoon meadow with parallax layers, runner, fence and SVG vector art,
  the game shows a photo-realistic spoon and egg from directly above on a white studio background or on the live rear
  camera image. "Spoon fills the lower 40 %" became "spoon fills most of the screen", because without a landscape the
  spoon is the whole game view. Parallax layers and the runner are dropped; footsteps show up as a very subtle bob.
- **Realistic artwork is procedural** (`EggscapeArt`, pure Swift) instead of hand-made SVG: photo-real shading cannot be
  expressed well in the SVG subset that asset catalogs support, and generating eggs from data makes every shop skin
  cheap to add. UI icons are SF Symbols. Any procedural image can be replaced by a real photo (PNG) later.
- **The owner's reference photo of a brown egg is not committed**, because its license is unknown. It was only used
  to judge realism.
- **Global leaderboards and in-app purchases are now in scope** (out of scope in the original spec): Game Center
  leaderboards, and consumable coin packs via StoreKit 2. Skins are bought with coins, which are earned by playing or
  bought as packs. Coins and skins are stored locally (no cloud save, as in the original spec), so they are lost when
  the app is deleted; consumable purchases cannot be restored by design.
- **Navigation** is a tab bar (Einzelspieler, Mehrspieler, Bestenliste, Shop) instead of the start screen with
  Spielen / Mehrspieler / Einstellungen / Anleitung. Settings and the tutorial open from a toolbar button.
- **Camera mode** needs `NSCameraUsageDescription`. The camera image is only shown on screen, never recorded, stored
  or sent, so the privacy label stays "Data Not Collected". The prompt appears only when the player turns on camera
  mode. (Since 2026-10-29 the camera is the default, see "Steering and camera by default" below.)

## Later decisions

- **Art tournament.** Three agents built competing procedural renderers. All three eggs matched the reference photo
  closely; candidate A (physically based: exact surface of revolution, analytic studio lighting) won because its skin
  system was complete. The spoon, the broken egg and the weather effects were finished afterwards on top of it.
- **App icon** is rendered from the same spoon and brown egg as the game (`eggscape-art icon`, `make icon`), laid
  diagonally on the warm yolk gradient of the first, hand-drawn icon. The egg has the game's proportions (1.44 bowl units, it
  nearly fills the bowl), so it reads well at home-screen size. The launch screen color is the system's
  grouped background (light and dark), which the first tab shows.
- **Coins.** Single-player runs earn coins (`CoinRewards`); hot-seat turns earn none (several people share one
  phone and wallet); nearby races earn coins including the place bonus once the host announces the results.
- **Egg prices (owner, 2026-10-28).** Only the classic white egg is free; every other egg is locked until it is
  unlocked with coins. The owner asked for the brown egg to cost about one game and for the others to get
  exponentially harder. So the brown egg costs 55 coins, at the time exactly what a clean 150 m time trial in calm
  weather paid, and every following egg in catalog order costs about 1.3 times the one before (each step between
  1.25× and 1.35×), rounded to friendly numbers: 55, 70, 90, 120, 160, 200, 260, 350, 450, 600, 750, 1,000, 1,300,
  1,700, 2,200, 2,800, 3,600, 4,800 and 6,000 for the rainbow egg. 1.3 is the factor that turns 19 paid eggs into a
  ladder from one run to a long-term goal: the first eggs take one to a few runs each, from about the twelfth on each
  egg alone is a goal of many runs, or a coin pack. A factor of 1.5 would put the last egg above 80,000 coins, 1.15
  below 700. All eggs together cost 26,505 coins. The tier bands (common 50–400, rare 450–2,000, epic 2,200–4,000,
  legendary 4,500–7,500) follow the ladder. Testers who got the brown egg for free in earlier builds keep it, because
  wallets store it with the owned eggs.

  The courses were shortened later (see below) with prices and rewards left as they were, so for a while a run paid
  less, and the 15 m course, at 28 coins in 5 s, paid the most per second. Then the coin rewards were made to follow
  the course length (see below), with the prices unchanged: a clean 100 m time trial in calm weather pays 55 coins
  again, exactly the brown egg, in about 34 s, and the shorter courses pay about as much per second (8 coins over
  15 m, 28 over 50 m). From the twelfth egg on each one alone takes 19 to 110 clean 100 m runs (10 minutes to an
  hour of play), and all eggs together about 480 of them, four and a half hours.
- **Coin packs** stay at 600 / 2,000 / 5,000 coins for the suggested 0.99 / 2.99 / 5.99 €: the small pack buys any
  common egg, the medium one any rare egg, the large one any egg but the last, which takes the large pack plus 1,000
  coins (about 18 clean 100 m runs in calm weather, ten minutes of play). Bigger packs give more coins per euro (606,
  669, 835). The "Bestes Angebot" badge goes to the pack with the most coins for the money at the prices StoreKit
  reports for the player's storefront, so it stays right if a storefront is priced differently.
- **Shop layout.** The shop stays one tab (the app keeps its four tabs) with two pages, "Eier" and "Münzen", picked
  with a segmented control. The page is kept in `AppNavigation`, so the coin balance, the "Münzen kaufen" button of
  the not-enough-coins alert and the screenshot staging can open the coin page. Locked eggs show their real look with
  a padlock in front of them rather than a silhouette, so players see what they save for: the padlock is filled with
  the accent color once the balance covers the price and frosted while it does not. Unlocking an egg also puts it on,
  as buying did before.
- **Game Center.** The player is signed in silently at launch (not in UI tests or screenshot mode), so scores reach
  the leaderboards right after a run and an accepted invitation opens the online room, also when it launched the app.
  Apple's sign-in sheet, if GameKit asks for one, waits until Bestenliste or Online opens instead of popping up over a
  run. Scores reached while signed out are submitted from the personal bests right after signing in. Time-trial
  leaderboards take the best time of any weather, because one board per weather option would split the few players.
- **MultipeerConnectivity warnings.** The deprecation warnings are silenced only inside `MultipeerTransport.swift` with
  `@diagnose(DeprecatedDeclaration, as: ignored)`, guarded by `#if hasAttribute(diagnose)` so older compilers (CI)
  still build it, just with warnings.
- **Nearby join data.** A joiner sends its player id, nickname and egg skin as the MultipeerConnectivity invitation
  context, so the message set of the spec needs no extra "hello" message.
- **Race time in multiplayer** is measured on the wall clock from the shared start, so a phone that was briefly in
  the background does not report a shorter time. The finish order is the arrival order at the host, as specified.
- **Screenshots** are staged scenes (`--screenshot-mode start|calibration|run-sunny|run-rain|run-storm|lobby|results|
  shop`) with ephemeral data and fixed seeds; the nearby lobby is a demo without networking. Camera mode cannot be
  captured in the Simulator, so the screenshots use the white background.
- **Localization.** German keys are the German text; where one German word needs two English translations, the key is
  semantic with a German default value (e.g. `pause.resume` = "Weiter" → "Resume", while "Weiter" → "Next").
  `make strings` fails if any UI string lacks an English translation.
- **Shorter time trials (owner, 2026-10-29).** Kurz, Mittel and Lang are 15, 50 and 100 m, the lengths of a real
  egg-and-spoon race, instead of 150, 300 and 600 m; a clean run takes about 5, 17 or 34 s. Only the distances
  changed: the speeds, the race mode, the coin formulas and prices, every weather tunable, Endlos and the leaderboard
  ids stay (the coin bonuses were scaled to the course length right after, see the next entry). Best times are
  stored under a new key, and those of the longer courses are deleted at the first launch instead of read: personal
  bests know a distance by its name only, and a 150 m time is no best for 15 m and must not reach that leaderboard.
  The Endlos record stays. The protocol version went to 3, so phones with the old lengths cannot race phones with the
  new ones; nearby rooms now advertise that version (earlier builds advertised 1 whatever their version), so such
  phones do not even list each other's rooms. Times from the longer courses that already reached Game Center stay on
  the same boards; each is slower than any run over the new lengths, so they rank last. With the weather unchanged,
  the short courses see less of it (`docs/TUNING.md`): on 15 m no puddle and, unless two eggs break, no lightning.
- **Coin rewards follow the course length (owner, 2026-10-29).** On the shorter courses the flat bonuses (15 coins
  for the finish, 10 for losing no egg, 20 for a personal best, 25 / 15 / 10 / 5 for the places) made up most of a
  run's coins: a clean 15 m run paid 28 coins in 5 s, the 100 m run 45 in 34 s, so the short course paid over five
  coins per second, four times the rate of the long one, and was a farm. The owner asked to pay roughly by play time
  again and for the brown egg to cost about one game again. So the time-trial bonuses are set for 100 m of course
  and paid in proportion to the course length, rounded half up: in full on 100 m, half on 50 m and 15 % on 15 m; a
  longer course would get more in the same proportion. Per 100 m they are 20 coins for the finish, 15 for losing no
  egg, 20 for a personal best and 25 / 15 / 10 / 5 for places 1 to 4. Unchanged: a coin per 5 m in every mode, the
  weather multipliers (wind 1.2, rain 1.3, storm 1.6, Zufall 1.4) on the distance, finish and no-egg-lost coins,
  personal-best and place bonuses on top of the weather, at least two players for a place, no coins for hot-seat
  turns, every price, the coin packs and the wire format (each phone computes its own coins, so the protocol version
  stays 3). Endlos pays exactly as before: 0.6 coins per second and a flat 20 for a record. A clean run in calm
  weather now pays 8 coins over 15 m (3 for the distance + 3 for the finish + 2 for no broken egg), 28 over 50 m
  (10 + 10 + 8) and 55 over 100 m (20 + 20 + 15), about 1.6 coins per second on every course. A personal best adds 3,
  10 or 20; the places pay 4 / 2 / 2 / 1 over 15 m (second and third tie after rounding), 13 / 8 / 5 / 3 over 50 m
  and 25 / 15 / 10 / 5 over 100 m. In bad weather a clean 100 m run pays what the old 150 m run paid: 66 coins in
  wind, 72 in rain, 88 in a thunderstorm, 77 with Zufall. The brown egg (55) costs exactly one clean 100 m run; a new
  player's first one pays 75 with the personal best, enough for the brown egg or the quail egg after it (70), and
  first clean runs over 15 and 50 m pay 11 and 38. All 19 paid eggs (26,505 coins) take about four and a half hours
  of clean 100 m runs. Wallets keep their coins.
- **Steering and camera by default (owner, 2026-10-29).** The owner found the egg too sluggish and asked for the default
  sensitivity to be 2.5 times as strong, with the slider left as it is, and for the camera to be the default background.
  So `TiltCalibration` applies a base gain (`GameConfig.tiltGain` = 2.5) in front of the setting: the slider keeps its
  70–130 % and its 100 % default, a stored value keeps its place on it, and every value steers 2.5 times as strongly as
  before (`docs/TUNING.md`). The dead zone (0.5° of the phone) and the 30° clamp stay. The gain is local input mapping,
  so the protocol version stays 3; finger steering in the Simulator is not affected. Fresh installs and "Daten
  zurücksetzen" start with the camera background. A background the player picked is stored and kept; installs that never
  picked one had the white default implicitly (nothing was stored) and now get the camera too, since a stored choice is
  the only way to tell a choice from the old default. The camera prompt appears on the calibration screen of the first
  single or hot-seat run, the first moment the camera is needed, and not during a race's countdown, which it would cover
  while the others run on. Without a rear camera (the Simulator) the app does not ask at all and shows the white
  surface. Answering the prompt with "no" shows the white surface and sets the background to Weiß, so the settings show
  what the player sees; choosing Kamera again explains how to allow it in the iOS settings. For the same reason "Daten
  zurücksetzen" leaves the background on Weiß while iOS still denies the camera: resetting the data does not reset the
  permission. UI tests and staged screenshots set the white background explicitly.
- **Tutorial asks for the name (owner, 2026-10-29).** The owner asked for a bigger "Überspringen" button and for the
  tutorial to end by asking for the player's name. "Überspringen" is now a bordered (Liquid Glass) button of at least
  44 pt in a bar of its own above the pages, so it cannot cover their text at any text size. After the three steps
  comes a fourth, "Wie heißt du?", with the current name filled in; "Überspringen" and "Weiter" on the third step lead
  there instead of closing the tutorial, so every new player is asked once, and the step itself has nothing to skip.
  "Los geht’s" (or Return) stores the name trimmed; empty stays allowed and keeps the "Spieler" fallback, as in the
  settings. The name step is a screen of its own rather than a fourth page of the paged `TabView`, because resizing a
  paged `TabView` for the keyboard is prone to layout glitches; its field and button sit below the scrolling text, so
  the keyboard pushes both up and hides neither. The keyboard comes up by itself only while the name is empty. The
  new `-first-launch` launch argument simulates a new install with throwaway data, for the tutorial's UI test and for
  manual checks.
- **Nearby join failures (owner, 2026-10-29).** Joining a listed room from the iPhone 18 Pro Simulator said "Der Raum
  ist voll oder das Rennen läuft schon." although the room was neither. That text stood for every failed join, but the
  host only advertises while it takes players, so for a listed room the likelier cause is a connection that could not be
  set up, which MultipeerConnectivity between the Simulator and a device often fails at (the Simulator has no Bluetooth
  or peer-to-peer Wi-Fi). The joiner cannot tell a declined invitation from a failed connection, so it now reads
  "Beitreten hat nicht geklappt …", which names both and what helps; "Der Raum ist voll." stays for a lobby that really
  has no seat. Three gaps in the join were closed: once the host had connected, the transport's invitation deadline was
  over, so a lobby that never came left the joiner on "Verbinde …" for good (now it gives up after 10 s); a connection
  that broke before the lobby came ended on the "Verbindung verloren" screen instead of the room list; and a retry could
  be turned down for the last seat because the host still counted the same phone's earlier attempt
  (MultipeerConnectivity keeps the peer id across attempts). Both sides log why a join failed: the joiner the reason and
  how many seconds it took, the host why it turned an invitation down or could not seat a phone that had connected.
  Nothing pointed at the protocol or at the required encryption (both sides ask for it, with no identity), so both stay
  as they were. `NearbySession` takes its nearby transport as a `NearbyTransport`, so its join logic is tested with a
  fake.
- **Coin shop and the Apple Account (owner, 2026-10-29).** The owner found that buying coins "does not work" and asked
  whether buyers should sign in with their Apple Account so that a purchase is not lost. They need not: StoreKit always
  buys with the Apple Account the device uses for the App Store, and the app never sees it. A purchase is not lost even
  if the app dies before crediting it: the transaction stays unfinished, and StoreKit delivers it again at the next
  launch (`Transaction.unfinished`, `Transaction.updates`), which the wallet credits once per transaction id. What is
  lost is the coins themselves when the app is deleted: they live in `UserDefaults`, and coin packs are consumables,
  which Apple does not restore. Keeping them would take a sync of the wallet, with the iCloud key-value store (small,
  enough for a balance, owned eggs and the credited transaction ids) or CloudKit; both need the iCloud capability, which
  a free Personal Team cannot use, so it waits for the paid Apple Developer Program, as do real purchases (the packs
  must exist in App Store Connect). Not built now. No bug was found in `StoreService` or the coin page, the scheme's
  StoreKit path resolves (Xcode reads it relative to `Eggscape.xcodeproj/project.xcworkspace`, hence `../../`), and the
  configuration sells exactly the three packs as consumables. Xcode's own run logs on the build Mac show that the
  configuration reached the iPhone 18 Pro Simulator in a run with the debugger off ("StoreKit Configuration sync"), and
  the Simulator's log shows the app loading the three packs from it in that run, while both logged runs on the iPhone
  failed to launch (Developer Mode off, then an untrusted developer certificate) and so synced nothing, which leaves an
  app opened from the Home Screen asking the real App Store. So the Run scheme keeps running without the debugger, and
  no second scheme was added. The storekit file is now also a resource of the unit tests, which buy a pack in a
  StoreKitTest session. Launches with throwaway data (`-ui-testing`, `-first-launch`, staged screenshots) do not listen
  for StoreKit's unfinished and updated transactions, so none of them is finished into a wallet that the next launch
  wipes; StoreKit keeps them for the next normal launch.
- **Help and legal links (2026-11-03).** App Review asks for a privacy policy link and a way to contact the developer
  inside the app (guidelines 5.1.1(i) and 1.5), and § 5 DDG probably for a legal notice (Impressum) that is easy to
  reach. So the settings end with "Hilfe & Rechtliches": "Datenschutz", "Support & Impressum" (support and the legal
  notice share one page) and the version. The rows open the project's GitHub Pages site (`site/`) in Safari, the German
  pages when the app runs in German and the English ones otherwise, so the pages speak the app's language. The
  addresses live in `WebPages` (`SettingsView.swift`), are the ones App Store Connect gets, and a unit test pins them.
- **Coins live on this device, and the app says so (2026-11-03).** Coins and eggs stay in `UserDefaults` without a
  cloud copy (see "Coin shop and the Apple Account"), and the App Store does not restore coin packs, so deleting the app
  or "Daten zurücksetzen" also deletes coins that were bought. The Münzen page says so under the packs, and the footer
  and the question of "Daten zurücksetzen" name bought coins. The reset now also forgets the nearby peer ids, which are
  stored per player name (`nearby.peerID.<Name>`), so no earlier name stays on the device.
- **English for every other language (2026-11-03).** iOS shows an app in the first of the player's languages it has,
  and otherwise in the language `CFBundleDevelopmentRegion` names. That was German (`$(DEVELOPMENT_LANGUAGE)`), so a
  phone set to, say, only French showed the German app. For a worldwide release English is the better guess, so the key
  is now `en` in `App/Info.plist`. German stays the source language of the String Catalogs (`developmentLanguage: de`
  in project.yml): the German texts are the keys, and German and English phones get their own language as before. One
  catch: a German phone looks for the permission texts in the German `InfoPlist.strings` and, without one, takes the
  English one of the fallback language. The build writes the German table only because the German entries of
  `InfoPlist.xcstrings` are marked translated, and `InfoPlistTests` fail if it goes missing. Checked in the Simulator:
  launched with `-AppleLanguages (fr)` the app is English, with `(de)` German and with `(en)` English, and the
  Info.plist and link tests pass with the test language set to de, en and fr. Setting the key back to
  `$(DEVELOPMENT_LANGUAGE)` restores the German fallback. The App Store page's language is chosen in App Store Connect
  (Primary Language) and is not affected.
- **Nearby help and a fresh search (2026-11-03).** A joiner without a room waited on "Suche Räume in der Nähe …" and
  a host alone in its room saw a disabled "Rennen starten", neither with a reason. iOS has no API that tells an app
  whether it may use the local network, and it may turn down the first advertising or browsing while its Local Network
  prompt is still up, leaving it to the app to try again (TN3179), so on two fresh installs, as App Review tests, a
  room could stay invisible until the player left and came back. Now the phone starts over when the app is active again (the
  prompt makes it inactive) if it has found nobody yet: the search while the room list is empty, the advertising while
  the host is alone. A list with rooms or a room with players is left alone. When MultipeerConnectivity reports that
  advertising or browsing did not start, the phone tries again after 2 s, then 4, 8 and 16 s and every 30 s after
  that, so a phone without Local Network access does not try every moment; before, it ended on "Verbindung verloren"
  with the raw error. After 10 s with nobody, the room list or the lobby names "Lokales Netzwerk" as the likely cause
  (the app cannot ask iOS) with "Einstellungen öffnen" for Eggscape's page in the iOS Settings, and the host alone
  reads "Warte auf Mitspieler …" with "Auf den anderen Handys: Mehrspieler → In der Nähe → Beitreten." The texts say
  "Handy" like the rest of the app, not "iPhone". The existing footer of the room list already asks for "Raum
  erstellen", so the joiner's hint adds only Local Network. Not yet checked on two fresh devices.
- **Numbers from other phones are checked (2026-11-03).** JSON carries no NaN or infinity, but it does carry 1e300,
  and converting such a distance or time to `Int` for the HUD or the results traps, as does waiting for a start that
  far away, so a modified client could crash every other phone in a race (online matches include strangers). Now a
  receiver drops a message with numbers no real phone sends (`NetMessage.isPlausible(eggsPerRun:)`): distances from 0
  to 10 000 m, race times from 0 to 3 600 s, egg counts from 0 to the eggs of a run, places from 1 to 4, and finite
  clock readings. The referee ignores reports outside the same bounds, a joiner waits 0.5 to 10 s for the start signal
  whatever its clock estimate says (3 s when it gives no number), and `RaceFormat` shows any number without trapping.
  A real race covers at most 100 m in well under a minute, so legitimate messages always pass; the wire format and the
  protocol version stay as they are.
- **Safety note and the camera question (2026-11-03).** The store texts and the calibration speak of running with the
  phone held flat, but the run moves by itself (no step detection), so nobody has to run while looking at the screen,
  and App Review guideline 1.4.5 asks apps not to invite risky use. Until the owner decides whether players should stand
  or move, the app says both: "Im Spiel läufst du von selbst, du kannst also auch im Stehen spielen. Wenn du
  mitläufst, dann nur, wo Platz ist, und achte auf deine Umgebung." (`SafetyNote`) on the tutorial's first page, on
  the calibration screen and under the race lobby's ready button, where racers calibrate. The camera prompt of a fresh
  install used to come the moment the first single or hot-seat run opened, before its calibration screen could say why.
  Now that screen first reads "Gleich fragt iOS nach der Kamera" with what the camera is for and that without it the
  game is white, and its "Weiter" brings up the prompt. It is still the first moment the camera is needed, and races
  still never ask. Following Apple's guidance for a screen before a permission prompt, "Weiter" is its only button:
  "Abbrechen" returns once the player has answered, either way, as it did when the prompt covered the screen. The
  purpose string no longer speaks of a "Kamera-Modus" the player never chose. When iOS denies the camera after the
  player chose it (a later "no" in the iOS settings, or a restricted device), the settings used to show Kamera with no
  hint while every run was white, and tapping the selected segment did nothing. Now the choice stays and a row under
  the picker says why the runs are white, with "Einstellungen öffnen"; the alert that switched back to Weiß is gone. A
  "no" in the prompt itself still picks Weiß, and "Daten zurücksetzen" still picks Weiß while iOS denies the camera.
- **Purchases through SwiftUI's purchase action (2026-11-03).** The coin shop bought with `Product.purchase()`, which
  gives StoreKit no window to show its sheet over. Apple's documentation recommends `PurchaseAction` for SwiftUI apps
  (from iOS 17, the deployment target), and on iOS 18.2 `purchase()` was reported to fail with "Could not get
  confirmation scene ID" when other windows were up, as Game Center's can be. So a coin card now buys through the
  `purchase` action of its environment and hands the answer to `StoreService.purchase(_:with:)`, which verifies,
  credits, finishes and reports errors as before; `Transaction.updates` and the unfinished transactions at launch are
  unchanged. The unit tests buy through the same entry point with `Product.purchase()` in a StoreKitTest session, and
  play the other answers (pending, cancelled, errors) with a stand-in. The sheet itself can only be checked by hand,
  with TestFlight, ideally also on iOS 17 or 18.
